# 任务：从头验证 Sesa 这个产品的设计与代码

你所在的工作目录**就是 Sesa 的完整源码**（`src/sesa/`、`tests/`、
`DESIGN.md`、`README.md`）。你可以读任何文件、改任何文件、跑任何命令。

Sesa 自称是"多 Agent 议事引擎"，它的四条设计底线写在 README 里：

1. 不设裁判——达成共识时共识本身就是产出，未达成则并列各方立场
2. 没确认到同意 ≠ 同意——default-deny，只有可解析的显式 agree 才算已解决；
   "有人反对"与"引擎没测到"分开记账
3. 卡死 ≠ 统一——终局分六档，deadlock / exhausted 绝不写成共识
4. 结论要连着前提一起交付；未决分歧要带出路

## 你要回答的

**这些底线，代码真的做到了吗？**

请给出**具体的、可核验的**发现。每一条必须包含：

- **位置**：`文件:行号`
- **失败场景**：什么输入 / 什么状态下，会得到什么错误结果
- **核验方式**：怎么证明它是真的

## 硬性要求

**空口无凭。** 你可以直接运行：

```
PYTHONPATH=src <你的python> -m pytest -q          # 现有的全部测试
PYTHONPATH=src <你的python> -c "..."              # 任意实验
```

**注意：跑测试时必须带 `PYTHONPATH=src`。** 否则会导入到工作副本之外的
另一份 sesa，你改了什么都看不见，测试永远是绿的——这个陷阱本项目已经
真实踩中过一次。

最有说服力的发现形态是：**写一个新测试，它在当前代码上失败**。
能做到这一步的，请把测试文件直接写进工作目录。

## 不要做的

- 不要泛泛评价"架构清晰""可维护性好"，那不是发现
- 不要把"我觉得应该改成 X"当成缺陷，除非能说出现在这样会错在哪
- 复现不了的，明确说这条不成立——**报不出问题是合格的答案**，
  编一个出来不是
