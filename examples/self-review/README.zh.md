# 让 Sesa 审自己（也可以用来审你的项目）

> [English](README.md) · **中文**

这套配置在 Sesa 自己身上跑过多轮，找出的每一条缺陷都留在了
`tests/test_bottom_lines*.py` 里——**测试名就是发现清单**，
数一数就知道有多少条，不需要我在这里写一个会过期的数字。

它们无一是作者自查发现的。

它同时是这个项目**唯一覆盖「真跑一整场」的测试**：每跑一次，
适配器、git worktree、执行证据、共识判定、交付渲染都被真实演练一遍。
今天有三个 bug 就是这么撞出来的，其中一个（TTY 渲染崩溃）在 pytest 里
永远看不到——因为测试跑在非终端下。

## 为什么议题要写成这样

**不要问「这个设计好不好」。** 那必然收到一份读起来很有道理、
但无从核实的读后感。要问**可被机械核验**的问题：

> 你在 README 里承诺的那几条，代码真的做到了吗？

并强制每条发现给出 `文件:行号` + 失败场景 + 核验方式，
**最有说服力的形态是一个在当前代码上失败的测试**。

## 为什么外挂一个扫描工具

模型单独读代码找不出多少。给它一份**外部工具**的扫描结果，
它就有了不来自作者框架的攻击面。

**报告通过 `--file` 进任务描述，所有参与者都看得到。**
早前这里用的是 `briefing`（每人私有的材料），理由是"制造信息不对称"——
那是为做实验造出来的场景。真实用法里你手上有一份扫描报告，
**没有任何理由只给其中一个人看**，要给就都给。

> 注意：不要用同一个模型既当参与者又当扫描器。
> 外部工具的价值就在于它不是从你的框架里长出来的。

## 跑

```bash
# 1. 外部扫描（任何能输出 file:line + 说明的工具都行）
ocr scan --path src/yourpkg --format json > /tmp/scan.json
python3 to_briefing.py /tmp/scan.json > /tmp/findings.md

# 2. 议事——扫描结果与议题一起进 --file，所有参与者都看得到
cat review-task.md /tmp/findings.md > /tmp/task.md
sesa run --repo . \
  --verify "PYTHONPATH=src python -m pytest -q" \
  --file /tmp/task.md \
  "README 里承诺的那几条，代码真的做到了吗？"

# 3. 把参与者写下的测试捞出来（失败的那一轮也有产出）
git branch --list 'sesa/*'
```

## 这份配置会随代码一起变

**议题模板里不要写死可推导的事实。** 本文件第一版就写了「现有 264 个测试」
和「前两轮共 22 条」，两天后两个数字都错了——而参与者会把错的前提当真。

所以：
- 「已修清单」改成**指向 `tests/test_bottom_lines*.py`，让参与者自己去读测试名**
- 测试总数不写，让参与者自己跑
- `tests/test_self_review_example.py` 会检查这份文档有没有重新写死数字

同样的道理适用于你的项目：**议题里凡是能从仓库读出来的，就别抄一份。**

## 三个必须注意的坑

**一、`--verify` 会不会跑到别处的代码。** 仓库被 `pip install -e` 装过之后，
在 worktree 里跑 pytest 导入的是**原仓库**，参与者改了什么都看不见，
测试永远绿——整个证据层静默失效。所以命令里要带 `PYTHONPATH=src`。
（引擎会检测并警告，但别依赖它兜底。）

**二、失败的一轮也有产出。** 参与者的发言可能因为额度、超时而失败，
但它在 worktree 里写下的文件已经提交到分支上了。
本项目第一轮的 8 个缺陷，就是从一轮「失败」里捞出来的。

**三、逐条机械核验，不要照单全收。** 四轮里报出的每一条我都亲手复现过。
外部工具会误报（第三轮里参与者明确否掉了 2 条），
参与者也会把工具的话原样转述。**结论是核验出来的，不是投票出来的。**
